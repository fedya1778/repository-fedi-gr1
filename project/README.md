- **Краткое описание (2-4 предложения):**  
  
Проект посвящён построению сервиса оценки кредитных рисков в сфере BNPL (Buy Now Pay Later) на основе данных о пользователях и транзакциях.
Используются исторические очищенные данные, модель градиентного бустинга LightGBM для бинарной классификации, логистическая калибровка вероятностей в скоринговые баллы и жесткие бизнес-правила.
Результат – REST API на FastAPI с поддержкой логирования и мониторинга, который по данным клиента возвращает его кредитный балл, вероятность дефолта и статус риска.

## 2. Структура проекта

Проект организован в следующей структуре:

- `requirements.txt` – зависимости проекта (библиотеки Python, необходимые для запуска).
- `report.md` – отчёт по проекту (постановка задачи, данные, эксперименты, результаты).
- `self-checklist.md` – чеклист самопроверки проекта перед сдачей.
- `notebooks/` – экспериментальные ноутбуки:
  - EDA, прототипы моделей, отдельные эксперименты.
- `src/` – основной код проекта:
  - `src/data` модули для работы с данными;
  - `src/models` обучение моделей;
  - `src/features` препроцессинг;
  - `src/service` запуск сервиса/скриптов.
- `data/` – демонстрационные/учебные данные:
  - **только открытые, синтетические или обезличенные данные;**
  - при необходимости – небольшие выборки для быстрого запуска.
- `configs/` – конфигурационные файлы:
  - `.yaml`, `.json`, `.env.example` и т.п.
- `tests/` – тесты (юнит-тесты, простые проверки).
- `artifacts/` – сохранённые модели, отчёты, результаты экспериментов.

## 3. Требования и установка

### 3.1. Требования

- Python `>= 3.10` 
- Основные пакеты: fastapi==0.110.0, uvicorn==0.28.0, pandas==2.2.1, scikit-learn==1.4.1.post1, lightgbm==4.3.0, numpy>=1.24.0, joblib>=1.3.0, pydantic, shap, matplotlib, seaborn. Тесты требуют pytest и httpx. (Все перечислены в requirements.txt.)
- Системные зависимости: возможны нативные зависимости/компиляторы для lightgbm (например, build tools / C compiler) — установите system build tools при ошибках установки бинарных колёс.

### 3.2. Установка окружения

```bash
# Перейти в папку проекта
cd project

# Создать виртуальное окружение (опционально, но рекомендуется)
python -m venv .venv

# Активировать окружение:
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate

# Установить зависимости
pip install --upgrade pip
pip install -r requirements.txt
```

## 4. Как запустить проект

### 4.1. Запуск обучения модели

```bash
cd project
 
source .venv/bin/activate
python src/data/prepare_data.py
python src/models/trainer.py
```
В этом проекте обучение модели выполняется через `src/models/trainer.py`. По умолчанию модель обучается на `data/cleaned_bnpl_data.csv` и сохраняется в `artifacts/models/production_model.pkl`.        


### 4.2. Запуск сервиса (API/веб-интерфейс)

```bash
cd project
source .venv/bin/activate      # если используется виртуальное окружение
uvicorn src.service.api:app --reload --host 127.0.0.1 --port 8000
```
Сервис поднимается на:

- хост: `127.0.0.1`
- порт: `8000`

### 4.3. Эндпоинты сервиса

- `GET /` — базовая проверка работоспособности, возвращает сообщение.
- `GET /health` — проверка состояния сервиса, возвращает `model_loaded`.
- `POST /predict` — основной endpoint для предсказаний.

Пример запроса к `/predict`:
```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"Customer_Age":30, "Gender":"M", "Annual_Income":50000, "Credit_Score":700, "Purchase_Category":"Electronics", "BNPL_Provider":"ProviderA", "Purchase_Amount":150.0, "Device_Type":"Mobile", "Connection_Type":"WiFi", "Checkout_Time_Seconds":45, "Browser":"Chrome"}'
```
Ответ содержит поля:

- `credit_score` — скоринговый балл клиента;
- `probability_of_default` — вероятность дефолта;
- `status` — категория риска (`Low Risk`, `Medium Risk`, `High Risk`).

Каждый из сценариев можно протестировать через браузер или `curl`:

- `GET http://127.0.0.1:8000/`
- `GET http://127.0.0.1:8000/health`
- `POST http://127.0.0.1:8000/predict`

## 5. Данные

В проекте используется открытый синтетический набор данных BNPL dataset с платформы Kaggle, полностью обезличенный и сгенерированный искусственно для задачи кредитного скоринга (прогнозирования дефолта при покупках в рассрочку).

Размещение файлов:
data/ — в этой папке локально формируются итоговые файлы после запуска скрипта подготовки данных.

В соответствии с правилами, тяжелые исходные файлы данных не хранятся в Git-репозитории в виде сырых выгрузок, чтобы не перегружать историю коммитов. Оригинальный тяжелый датасет вынесен в облачную инфраструктуру проекта (GitHub Releases).

Инструкция по скачиванию и подготовке данных
Для того чтобы локально развернуть инфраструктуру данных, в проекте реализован полностью автономный скрипт автоматической сборки. Любому пользователю достаточно выполнить одну команду:

```Bash
python src/data/prepare_data.py
```
Что делает этот скрипт автоматически:
Подключается к удаленному хранилищу репозитория и скачивает оригинальный сырой датасет bnpl_dataset_v2.csv напрямую из релизов: https://github.com/fedya1778/BNPL-Risk-Scoring-Service/releases/download/dataset/bnpl_dataset_v2.csv.
Применяет к нему зафиксированную логику фильтрации аномалий из разведочного анализа данных.
Сохраняет полностью очищенный и готовый к обучению моделей LightGBM/бустингов файл по пути data/cleaned_bnpl_data.csv.

## 8. Ограничения и дальнейшая работа

На текущем этапе сервис реализован как минимально рабочий API для скоринга клиента, но есть важные ограничения:

- входной API `/predict` принимает произвольный JSON через `dict`, но не использует Pydantic-схемы для жесткой валидации полей и типов;
- нет проверки полного набора обязательных признаков, поэтому ошибки в запросах обрабатываются неявно;
- предобработка фич ограничена только приведением категориальных признаков к типу `category`;
- нет API-эндпоинтов для метрик, истории запросов, объяснения предсказаний или пакетной обработки;
- отсутствует аутентификация, авторизация, rate limiting и централизованное логирование;
- не реализована устойчивая обработка отсутствующих данных и неявных типов в запросах.

В качестве следующей работы можно сделать:

- добавить Pydantic-модели для запроса и ответа, чтобы `/predict` строго проверял входные данные;
- расширить пайплайн обучения;
- добавить версионирование модели и возможность выбирать/загружать разные артефакты;
- реализовать дополнительные API-эндпоинты, например `/metrics`, `/predict/batch`, `/explain` и `/model-info`;
- улучшить обработку ошибок и вернуть стандартные HTTP-статусы для некорректных запросов;
- внедрить аутентификацию/авторизацию и централизованное логирование для продакшн-сервиса;
- добавить докеризацию, CI/CD и тесты для контрактов API и обработки невалидных входных данных.
