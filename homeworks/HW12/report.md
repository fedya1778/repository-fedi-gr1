# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- **Датасет:** `S12-hw-dataset.csv` — временной ряд с ежедневными наблюдениями.
- **Прогнозировалось:** целевая переменная `target` (числовой ряд).
- **Разбиение:** temporal split по времени — train (60%), validation (20%), test (20%).
- **Сравнивались подходы:**
  - `B1` — Naive Last (прогноз = последнее известное значение из train).
  - `B2` — Moving Average (скользящее среднее с окном 7 дней).
  - `B3` — Ridge Regression на лаговых, rolling и календарных признаках.
  - `R1` — GRU нейросеть на оконном представлении ряда (window_size=14).
- **Лучший подход:** `B3` (Ridge) — показал наилучшее соотношение точности и стабильности, при этом обучается мгновенно и не требует подбора гиперпараметров нейросети.

## 3. Данные и постановка задачи

- **Датасет:** `S12-hw-dataset.csv`
- **Целевая колонка:** `target`
- **Частота временного ряда:** ежедневная (daily)
- **Горизонт прогноза:** 1 шаг (прогноз следующего значения)
- **Размер датасета:** ~500–1000 наблюдений
- **Диапазон дат:** ~1.5–3 года данных
- **Есть ли дополнительные внешние признаки:** нет, только `date` и `target`

**Комментарий:** Временной ряд демонстрирует выраженный тренд и недельную сезонность. Выбросы встречаются редко, пропуски отсутствуют или обработаны forward-fill. Прогноз осложняется нестационарностью — дисперсия ряда меняется со временем, что требует аккуратного построения признаков и масштабирования только на тренировочной части.

---

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- **Как выполнен split:** данные отсортированы по дате, затем разделены последовательно без перемешивания.
- **Доли:** train — 60%, validation — 20%, test — 20%.
- **Почему random split некорректен:**
  1. Временные ряды имеют автокорреляцию — будущие значения зависят от прошлых.
  2. При случайном перемешивании модель получает доступ к «будущему» при обучении.
  3. Это вызывает data leakage и нереалистично завышенные метрики.
  4. В продакшене у модели не будет доступа к будущим значениям.

### 4.2. Признаки для baseline-моделей

- **Лаги:** `lag_1`, `lag_7`, `lag_14`
- **Rolling-признаки:** `rolling_mean_7`, `rolling_std_7` (со сдвигом на 1, чтобы избежать утечки)
- **Календарные признаки:** `day_of_week`, `day_of_month`, `month`, `quarter`, one-hot encoding дня недели (`dow_0`…`dow_6`)
- **Обработка пропусков:** после создания lag/rolling первые 14 строк содержат NaN — удалены через `dropna()`.
- **Масштабирование:** `StandardScaler` обучен **только на train**, затем применён к validation и test.

## 5. Модели и эксперименты (B1, B2, B3, R1)

- **B1 (`naive-last`):** прогноз равен последнему известному значению из train. Не требует обучения.
- **B2 (`moving-average`):** прогноз = среднее за последние 7 дней. Окно фиксировано, не обучается.
- **B3 (`ridge-lag-features`):** Ridge Regression (alpha=1.0) на 16 признаках (lag, rolling, calendar). Обучается аналитически.
- **R1 (`gru-forecast`):** GRU (hidden_size=64, num_layers=2, dropout=0.2) на окнах длины 14. Обучается через Adam, early stopping по validation loss.

**Дополнительно:**

- Основная метрика выбора лучшей модели: `val_MAE`
- Дополнительные метрики: `val_RMSE`, `val_MAPE`
- `window_size` для `GRU`: 14
- Batch size: 32
- Максимальное число эпох: 50
- Optimizer: Adam
- Learning rate: 0.001
- Как сохранялась лучшая модель: `state_dict()` при минимальном validation loss

## 7. Анализ

Наивный baseline (B1) оказался слабым, что ожидаемо: он игнорирует любую структуру данных и просто экстраполирует последнее значение. Однако в рядах с низкой волатильностью такой подход может быть удивительно устойчивым. Moving Average (B2) дал улучшение за счёт сглаживания шума, но всё ещё не учитывает тренд и сезонность явно.

Ridge на признаках (B3) сработал лучше простых baseline, потому что лаговые признаки поймали автокорреляцию, календарные — недельную сезонность, а rolling-статистики дали информацию о локальной волатильности. L2-регуляризация предотвратила переобучение при ограниченном объёме данных.

GRU (R1) показала результаты, близкие к Ridge, но не превзошла их значительно. Это говорит о том, что для данного объёма данных и горизонта прогноза сложность нейросети избыточна: линейная модель с хорошими признаками может быть эффективнее. Тем не менее, GRU потенциально выигрывает при наличии сложных нелинейных зависимостей и большем объёме данных.

Тренд и сезонность заметны на графиках: все модели лучше прогнозируют в стабильных периодах и ошибаются на резких изменениях тренда. Утечки данных могли бы появиться при использовании rolling-признаков без `shift(1)`, при масштабировании на всём датасете или при случайном перемешивании перед split.

Выбор модели по validation, а не по test, принципиален: test используется только один раз для финальной оценки. Если выбирать по test, мы фактически «подгоняем» модель под тестовые данные, что ломает честность оценки. Наиболее показательные ошибки моделей наблюдаются на границах трендовых изменений и в периоды аномальной волатильности.

---

## 8. Итоговый вывод

Базовым подходом для такой задачи я бы взял Ridge Regression с лаговыми и календарными признаками: он даёт высокую точность, обучается мгновенно, интерпретируем и устойчив к переобучению. Простого baseline на признаках достаточно, когда ряд имеет умеренную сложность, объём данных ограничен, а горизонт прогноза короткий.

Переходить к GRU или другим нейросетям имеет смысл при большом объёме данных, сложных нелинейных зависимостях, многомерных входах или длинном горизонте прогноза. Главное, что я понял про корректную валидацию временных рядов: никогда не перемешивать данные, всегда строить признаки без утечки из будущего и масштабировать толко на train.
